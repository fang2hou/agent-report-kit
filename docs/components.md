# Components

This file decides **which component fits which content shape**. The markup itself is
generated by the renderer: never copy the HTML snippets below into a report — author
`report.json` per [report-schema.md](report-schema.md), where each component has a JSON
form. The snippets remain as a visual contract for what each component renders.

## Choose by content shape

Use one component per idea. If two components could show the same content, pick the first match in this table.

| The content is…                                                                | Use                                                                   |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| The result the reader must take away                                           | Summary box                                                           |
| A warning, risk, or decision the reader must notice                            | Callout (`warn`, `risk`, `ok`, plain)                                 |
| 2–4 numbers that carry the main finding                                        | Figures row                                                           |
| A few facts about one thing (owner, version, date)                             | Key-value list                                                        |
| Records with the same fields                                                   | Table                                                                 |
| One measure across a few items                                                 | Bars                                                                  |
| A trend or data plot                                                           | `xychart-beta` Mermaid via `tools/diagram.ts`, or generated chart SVG |
| A share of a whole                                                             | `pie` Mermaid via `tools/diagram.ts`                                  |
| An interaction order between parties                                           | `sequenceDiagram` via `tools/diagram.ts`                              |
| A branching process, a lifecycle, a data model, or a structure with many parts | Mermaid source through `tools/diagram.ts`                             |
| Style candidates the user must pick from                                       | `swatch` block plus a review question                                 |
| Options the reader weighs against each other                                   | Compare cards                                                         |
| An ordered procedure                                                           | Steps                                                                 |
| Text quoted from another language                                              | Pair                                                                  |
| Evidence most readers skip: logs, raw output                                   | Details                                                               |
| A status word inside a sentence or table cell                                  | Chip                                                                  |
| A question for the user                                                        | Review components                                                     |
| Anything else                                                                  | Paragraphs and lists; they need no box                                |

Most sections need only headings, paragraphs, and at most one component. A page where every block sits in a box reads as noise.

## Page frame

The renderer builds the frame from the top-level `report.json` fields: `kicker`, `title`, and `meta` become the masthead; `summary` becomes the summary box; each entry of `sections` becomes one `h2` plus its blocks.

Body text stays inside the reading measure — the line length readers scan without losing their place. Figures do not need `wide`: they start inside the measure and break out to about 1.35× automatically only when their intrinsic width overflows the column ("wide by need, not by default"). For other blocks set `wide: true` explicitly — a compare grid or a table with many columns — to let it break out to about 1.35× the measure: still anchored to the column, wide enough for side-by-side reading. Anything wider than the breakout scrolls horizontally inside an in-page slider that stays visible for as long as the region is scrollable (draggable, never displacing page elements). Use `wide` on a few blocks per page at most; if everything is wide, nothing stands out.

Every report has a table of contents behind a bare arrow fixed to the left edge (a bottom-left control on narrow desktop panels): hovering the arrow lifts it with a small shadow, clicking slides in a transparent panel clear of the arrow — plain semi-transparent entries with no background, the one being read carrying a soft gray pill. The panel follows the reading position and smooth-scrolls on click; with review questions present it includes the review area and each individual question. Each target has a unique anchor, even when generated and explicit section ids collide. Give a section an `id` when you want a stable anchor.

Write all visible text in the page language; keep `id`, `name`, and `value` fields as ASCII IDs.

On served pages the renderer also shows a status dot in the top left — gray when disconnected or the Agent is not listening, steady green only while an Agent has polled recently; hovering the dot grows a pill with the status text and the number of discussions whose last message is an Agent reply. A follow-up returns a discussion to pending. While the server is reachable the reader can select any text and send the agent a question, the answer shows as a hover card on the quoted passage, and every asked passage keeps a rounded soft-yellow highlight — dashed underline while the reply is pending, solid accent once answered.

## Reading components

Summary box, directly after the masthead:

```html
<section class="summary">
  <h2>Conclusion</h2>
  <ul>
    <li>
      <strong>Remove 3 packages</strong>: lodash, moment, classnames. This saves about 180 KB.
    </li>
    <li>zod 4 needs its own upgrade; it touches 14 files.</li>
  </ul>
</section>
```

Callout. Plain for notes; `ok`, `warn`, `risk` only when the status is real:

```html
<div class="callout warn">
  <p><strong>Upgrade zod 4 separately.</strong> It changes the shape of error messages.</p>
</div>
```

Chip, inside text or a table cell. Variants: `ok`, `warn`, `risk`, `accent`, or none for neutral:

```html
<span class="chip ok">Remove</span>
```

Steps, only for actions that must happen in order. Independent recommendations are a plain `<ol>` or a table:

```html
<ol class="steps">
  <li>Remove the three packages and run <code>pnpm install</code>.</li>
  <li>Run the full test suite and build.</li>
</ol>
```

Pair, for a quote in another language. The translation comes first, in the page language; the original keeps its `lang`:

```html
<div class="pair">
  <p class="tr">The error format changes in v4, so update form validation in the same PR.</p>
  <p class="orig" lang="ja">
    v4 ではエラー形式が変わるため、フォームの検証も同じ PR で更新してください。
  </p>
</div>
```

Details, for evidence. Printing opens every `details` automatically:

```html
<details>
  <summary>Search commands and full output</summary>
  <pre><code>$ rg -l "from 'lodash'" apps/web</code></pre>
</details>
```

Card, for a self-contained aside that needs a frame. Use sparingly:

```html
<div class="card"><p>…</p></div>
```

Key-value list, for a few facts about one thing. Use a table instead when several things share the same fields:

```html
<dl class="kv">
  <dt>Owner</dt>
  <dd>Frontend team</dd>
  <dt>Current version</dt>
  <dd>zod 3.23.8</dd>
</dl>
```

## Data components

Figures row, right after the summary when two to four numbers carry the main finding. Each figure backs a claim in the summary; scope counts (files read, commits scanned, days covered) are not findings and belong in `.meta`. Put the unit in the number and keep each label to a few words. Rows hold at most three figures: two or three sit side by side, four wrap into a 2×2 grid, and a single figure reads as a stat bar with a full-width rule above a larger number. Never add `wide` to a figures row:

```html
<div class="figures">
  <div><b>3 of 12</b><span>dependencies removable</span></div>
  <div><b>180 KB</b><span>expected savings</span></div>
</div>
```

Table. Always wrap it so wide tables scroll instead of breaking the page. Right-align numbers with `num`, and put dates in `<time>`; neither wraps inside its cell:

```html
<div class="table-wrap">
  <table>
    <thead>
      <tr>
        <th>Package</th>
        <th class="num">Size</th>
        <th>Last used</th>
        <th>Verdict</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <td>moment</td>
        <td class="num">96 KB</td>
        <td><time>2026-10-16</time></td>
        <td><span class="chip ok">Remove</span></td>
      </tr>
    </tbody>
  </table>
</div>
```

Bars, for one measure across up to about 12 items. Set each `--v` to value ÷ axis maximum as a percentage, using one maximum for all bars; sort by value and print the value:

```html
<div class="bars">
  <span>moment</span><span class="track"><i style="--v: 53%"></i></span
  ><span class="v">96 KB</span> <span>lodash</span
  ><span class="track"><i style="--v: 40%"></i></span><span class="v">72 KB</span>
</div>
```

Compare cards. All cards are white with a solid hairline border; mark the recommended one with `pick` and a chip — it differs only by that chip and a faint accent-tinted dashed border. Keep pros and cons to three lines each:

```html
<div class="compare wide">
  <article class="pick">
    <h3>Upgrade at once <span class="chip accent">Recommended</span></h3>
    <p>One PR changes all 14 files.</p>
    <ul class="pros">
      <li>Changes in one place, easy to review</li>
    </ul>
    <ul class="cons">
      <li>Large PR, about 400 lines</li>
    </ul>
  </article>
  <article>…</article>
</div>
```

## Diagrams and images

Every chart and structured diagram — flows, lifecycles, interaction orders, data models, file trees — lands as inline SVG in a `figure` block. Structural diagrams are authored in Mermaid and rendered by the kit's tool; data plots arrive as generated SVG from a chart library (pygal or similar). Either way a diagram adds no JavaScript of its own: the page embeds static SVG, and colors come from the page theme, not from the file.

For a diagram, write the Mermaid source and run the tool, then put the resulting SVG in the `figure` block's `svg` field:

```
flowchart TD
    A[Christmas] -->|Get money| B[Go shopping]
    B --> C{Let me think}
    C -->|One| D[Laptop]
    C -->|Two| E[iPhone]
    C -->|Three| F[Car]
```

```bash
node tools/diagram.ts flow.mmd flow.svg   # Mermaid → themed SVG (Pele)
```

The output carries Pele's `.pele` root class; the renderer maps its theme variables onto the design tokens, so node fills, borders, edges, and text follow the page palette automatically — including the `lang`-specific font. Pie slices, chart series, and colored branches draw from `--pele-series-1`…`8`, mapped to the token hues. The same pipeline covers `pie` (share of a whole), `xychart-beta` (trends), and `sequenceDiagram` (interaction orders) — only the source changes. The example below is the mermaid landing-page flowchart: labeled edges, a decision node, three branches.

Rules that hold for every figure, generated or hand-written:

- The SVG must scale with the column: a `viewBox` plus `max-width: 100%` (tool output ships both — it keeps width/height hints but caps itself with an inline style).
- Text renders at 14 px or larger (the tool uses 17 px).
- Label lines and boxes directly; add a legend only when direct labels do not fit.
- Bars and areas start at zero. Say the unit in the caption.
- Avoid Mermaid `style`/`classDef` color overrides: they bake fixed hex values into the SVG and ignore the page theme. Shape and class hooks remain useful for structure; only colors are better left to the tokens.

Use a raster image only for something that cannot be drawn: a screenshot, a photo. Resize and compress it first (for example `cwebp -q 75 -resize 1600 0 in.png -o out.webp`), then embed it as a data URI or keep it as a file next to `index.html` and reference it with a relative path. A served directory serves sibling files; a plain report must embed.

## Style galleries

When the decision is "pick one of these looks", show the candidates instead of describing them: a `swatch` block renders each item's `html` — a small self-contained fragment like a button with its hover style — in its own cell, with an optional short label underneath.

```json
{
  "type": "swatch",
  "wide": true,
  "items": [
    { "label": "A · solid", "html": "<button type=\"button\" style=\"…\">Confirm</button>" },
    { "label": "D · pill", "html": "<button type=\"button\" style=\"…\">Confirm</button>" }
  ]
}
```

This is the one block that takes raw HTML by design; keep fragments small, token-based (`var(--color-accent)` and friends), and free of scripts. Reference tokens rather than hex values so candidates follow the theme, and pair the gallery with a review question whose options name the candidates.

## Review components

Every review component comes from the `review.questions` array in report.json — the snippets below show what the renderer emits, not what you write. The renderer adds the submit bar automatically. Field mapping: a question's `text` becomes the legend, `hint` the hint line, `options` the cards (`value` stays an ASCII ID, `label` is visible text, `desc` the cost line), `note: true` adds the note input, `cols: true` lays two or three short options side by side.

Single choice, as option cards:

```html
<fieldset class="q" data-required="zod-plan">
  <legend>How should we upgrade zod?</legend>
  <p class="hint">This sets the PR size and how it is reviewed.</p>
  <div class="options cols">
    <label class="option"
      ><input type="radio" name="zod-plan" value="all-at-once" /><span class="t">All at once</span
      ><span class="d">One PR, about 400 lines</span></label
    >
    <label class="option"
      ><input type="radio" name="zod-plan" value="per-form" /><span class="t"
        >One form at a time</span
      ><span class="d">5 PRs, both APIs live for a while</span></label
    >
  </div>
  <input type="text" name="zod-plan:note" placeholder="Note (optional)" />
</fieldset>
```

Multiple choice: the same markup with `type="checkbox"` and one shared `name`. The answer `value` becomes an array.

Verdict per item, for reviewing a list: one `fieldset.item` per item inside a `fieldset.q`. The verdict row sits to the right of the item name and hint, so keep each label to about four CJK characters or two English words. Offer only the verdicts that make sense for that item: an item with nothing to merge into gets no "Merge" verdict.

Tone classes give each verdict a meaning glyph and color by what the choice does: `ok` a check for the safe or unchanged outcome (keep, approve), `risk` a cross for a destructive or irreversible action (delete, reject), `warn` a clock for a deferral or partial answer (later, unsure). A verdict without a tone falls back to a plain dot in the accent color. Give the same verdict the same tone on every item, so a glyph and color mean one thing across the page:

```html
<fieldset class="q">
  <legend>Decide each package</legend>
  <fieldset class="item" data-required="lodash">
    <legend>lodash <span class="chip">72 KB</span></legend>
    <p class="hint">No imports left since the September 2026 refactor.</p>
    <div class="seg">
      <label class="risk"
        ><input type="radio" name="lodash" value="remove" /><span>Remove</span></label
      >
      <label class="ok"><input type="radio" name="lodash" value="keep" /><span>Keep</span></label>
      <label class="warn"
        ><input type="radio" name="lodash" value="later" /><span>Later</span></label
      >
    </div>
    <input type="text" name="lodash:note" placeholder="Note (optional)" />
  </fieldset>
</fieldset>
```

Free text, for an open question. Use `textarea` only when the answer may run longer than one line:

```html
<fieldset class="q">
  <legend>Anything else I should know?</legend>
  <textarea name="extra-notes" placeholder="Optional"></textarea>
</fieldset>
```

When an item quotes foreign-language text the user must judge (a memory entry, an issue title), show a `pair` block above the question so the translation sits above the original, and reference it from the item's `label` or `hint`.

## Read-through checklist

Use this when no browser can render the page:

- [ ] `lang` matches the page language; `title` states the finding; `summary` holds 2–5 points that agree with the sections.
- [ ] Every section heading states its point; every block is one idea in the simplest component that fits the content-shape table.
- [ ] Every `id`, `name`, and `value` is an ASCII ID; every visible label, option, and hint is in the page language.
- [ ] Every question and option in `review.questions` names a decision the user must make, and the recommended option comes first.
- [ ] Foreign-language quotes sit in `pair` blocks with `origLang` set, translation first.
- [ ] No raster image exceeds 1600 px or 200 KB; the compile step's printed size is within budget.
